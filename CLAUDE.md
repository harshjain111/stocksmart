# CLAUDE.md — Smokzy Inventory System

Build rules for this repo. Read this before writing any code. When something here conflicts with a prompt, **this file wins** — stop and flag it.

---

## What this is

A multi-branch inventory system for Smokzy: raw materials are bought, mixed into flavours by recipe, and distributed to godowns, offices, clubs and other cities. Departments raise requisitions, the store fulfils them by transfer or purchase, and everything received is booked through a Goods Receipt Note.

**Aim:** never out of stock anywhere, no leakage, minimum wastage — as the business scales to more cities.

---

## Stack

- **Next.js 15** (App Router) + **TypeScript** (strict)
- **Supabase** — Postgres, Auth, Storage, Row Level Security
- **Tailwind** for styling, **shadcn/ui** for primitives
- **Vercel** for deploy
- **Zod** for every input schema, **react-hook-form** for forms
- **TanStack Query** for server state

No other dependencies without asking.

`npm run dev` deliberately does **not** use Turbopack. Turbopack's dev HMR
leaves the client module graph out of step with the SSR one, which shifts
React's `useId` tree positions and makes every Base UI component that calls
`useId` report a hydration mismatch after any edit — noise that buries real
hydration bugs. Production builds are unaffected and still use Turbopack.
`npm run dev:turbo` is there if you want the faster cold compiles and can
live with the warnings.

## The ten rules that must never be broken

### 1. Everything is grams, as integers
All stock, all recipes' output, all transfers, all counts. `qty_g bigint`. Display converts to kg. **Never store a float quantity.** Rounding is done once, at display.

### 2. Stock is never written directly
`stock_balances` is only ever changed by a trigger reading `stock_movements`. No code path anywhere does `UPDATE stock_balances`. If a balance is wrong, it must be traceable to a movement.

### 3. Every movement has a reason and a reference
`stock_movements.reason` is an enum, `ref_type` + `ref_id` always point at the document that caused it. No orphan movements. Reasons:
`grn_vendor · grn_transfer · dispatch · batch_consume · batch_produce · count_adjust · transit_loss · club_sync · opening`

### 4. Stock moves on receipt, not on dispatch
Dispatch posts a negative movement at the sender. **The receiver's stock does not change until a GRN is raised.** The gap between dispatched and received is in-transit, and it is visible on its own screen. When a transfer is closed short, post a `transit_loss` movement so the ledger always balances.

### 5. Recipe versions are immutable
Once a `recipe_versions` row is inserted, its lines never change. There is no update endpoint. "Editing" a recipe inserts a new version. The only mutable field is `status` (`current` / `archived`). A new version requires a non-empty `note`. Percentages must sum to exactly 100 — enforce in a DB constraint, not just the UI.

### 6. Batches snapshot their recipe
`batches.recipe_snapshot jsonb` holds the full formula as it was that day. It is never derived from the version at read time. A batch's record of what went into it can never shift.

### 7. Nothing is ever deleted
No `DELETE` on any business table. Archive with `is_active = false` or a `status` column. Applies to materials, flavours, suppliers, departments, users, documents.

### 8. Access is enforced in the database
RLS policies on every table. The UI hiding a screen is not access control. In particular: **recipe_versions and recipe_lines are readable only by roles `admin` and `senior_mixer`.** A mixer hitting the API directly must get nothing back.

### 9. Every document is numbered and sequential
`REQ-0001`, `TRF-0001`, `PO-0001`, `GRN-0001`, `B-0001`, `CNT-0001`. Generated by a DB sequence per type, per financial year. Never client-generated, never reused.

### 10. Every read of a recipe is logged
Insert into `audit_log` on recipe version read, with user, flavour, version, timestamp. Also log: version creation, rollback, count adjustments, GRN discrepancies, requisition approvals.

## Data model

### Org
- `branches` — Guwahati (HQ), Kolkata. `is_hq` flag.
- `departments` — the stock-holding unit. Belongs to a branch. Flags: `holds_raw`, `holds_mixed`, `can_mix`. Has an HOD.
- `profiles` — user, role, `branch_id`
- `user_departments` — an HOD can own several departments

**A department is the only thing that holds stock.** There is no separate "location" concept. Club Nexa is a department. The Guwahati godown is a department. Keep it that way.

### Masters
- `suppliers`
- `raw_materials` — code `RM-xx`, default supplier
- `supplier_rates` — rate history; new row on every GRN, never an update
- `flavours` — code `FL-xx`, points at `current_version_id`
- `recipe_versions` → `recipe_lines`

### Stock
- `stock_movements` — the ledger, append-only
- `stock_balances` — derived, trigger-maintained
- `par_levels` — per department, per item

### Documents
- `requisitions` → `requisition_lines`
- `transfers` → `transfer_lines`
- `purchase_orders` → `po_lines`
- `grns` → `grn_lines` — one table for both vendor and internal receipts
- `batches` → `batch_consumption`
- `stock_counts` → `stock_count_lines`

### Integration
- `club_flavour_map`, `club_sync_log`

### `item_type` polymorphism
Movements, requisition lines, transfer lines, GRN lines and count lines all reference either a raw material or a flavour. Use `item_type enum('raw','flavour')` + `item_id uuid`. Do **not** create parallel tables for raw and flavour — it doubles every query for no gain.

## Roles

| Role | Scope |
|---|---|
| `admin` | Everything, all branches |
| `branch_manager` | Everything within their branch |
| `store_manager` | Stock, transfers, GRN, counts — their branch |
| `purchase_manager` | Suppliers, rates, POs, vendor GRNs. **Never recipes.** |
| `hod` | Their departments only: raise requisitions, receive, count |
| `senior_mixer` | Recipes (read all versions), batches, version selection |
| `mixer` | Assigned batch only, masked component codes |

Club staff are **not** users here. They stay in the club app.

### Masking
When a `mixer` opens a batch card, the API returns component **codes only** — no names, no percentages, no version number. Do this masking server-side. Never send the real names to the client and hide them with CSS.

## Document lifecycles

Implement these as explicit status enums with guarded transitions. No free-form status strings.

```
Requisition   draft → submitted → approved → fulfilling → closed
                            ↘ rejected
  per line decision: transfer | buy | mix_then_transfer | rejected

Transfer      draft → dispatched → received → closed
                                 ↘ short_closed  (posts transit_loss)

Purchase      draft → sent → partially_received → received → closed
  ship_to_department_id — may be a different branch (direct delivery)

GRN           draft → posted   (posting is what moves stock)
  source: vendor (against a PO) | internal (against a transfer)

Batch         draft → confirmed   (confirming is what moves stock)

Count         draft → submitted → approved  (approval posts adjustments)
```

Nothing moves stock until the document reaches its posting state. A dispatched transfer that never gets a GRN sits in transit and shows up on the in-transit report — that is the point.

## Buying logic

The "what to buy" engine:

1. Collect demand: approved requisition lines marked `buy`, plus manual entry, plus optional par top-up.
2. For flavour demand, net off mixed stock **at the fulfilling department**, explode the remainder using the flavour's **current** recipe version, apply that version's wastage %.
3. Net raw material need off stock at the department that will fulfil, plus open PO quantity already inbound to it.
4. Group the shortfall by each material's preferred supplier.
5. Draft one PO per supplier, with `ship_to_department_id` set — this is how Kolkata gets direct delivery.

**Never net Kolkata's requirement against Guwahati's stock** unless the reviewer explicitly chose `transfer` on that line. Branch stock is not fungible by default.

Rates are always editable — on the PO and again on the GRN. A blank rate is valid. The GRN rate becomes the new `supplier_rates` row.

## Leakage tracking

Four variances, one report. Build them as views.

| Variance | Compare | Catches |
|---|---|---|
| Transit | dispatched vs received | loss between branches |
| Mixing | planned vs actual component weights | over-pouring, spillage |
| Club | shishas sold × standard g vs actual consumption | leakage at outlets |
| Count | system vs physical | everything else |

## Code conventions

- `src/app/(app)/<screen>/page.tsx` — screens; `src/features/<domain>/` — logic
- Server Components by default. `'use client'` only where interaction demands it.
- All mutations are **Server Actions**, validated with Zod at the boundary. No API route unless something external calls it.
- Money is `numeric(12,2)`, rupees. Quantities are `bigint`, grams. Never mix them in one column.
- Dates as `timestamptz`, always. Display in IST.
- Never `select *` in application code — name the columns.
- Every table gets `created_at`, `created_by`, and where it matters `updated_at`.
- Migrations in `supabase/migrations/`, one concern per file, never edited after being applied.

## UI conventions

- Plain language. "What to buy", not "Procurement planning". "Send & receive", not "Logistics module".
- One primary action per screen, top right.
- Every quantity input shows its unit next to it.
- Destructive or irreversible actions need a typed confirmation, not just a dialog.
- Empty states say what to do next, not "No data found".
- Every list is filterable by branch and department for users who can see more than one.
- Mobile matters: HODs and store staff will use phones. Tables collapse to cards under 820px.

## Don't

- Don't add a feature that isn't in the PRD. Ask first.
- Don't create an "edit recipe" path.
- Don't let a GRN post more than was dispatched or ordered without an explicit over-receipt flag and a reason.
- Don't cache stock balances in the client beyond a query invalidation cycle.
- Don't build reporting on top of `stock_balances`. Build it on `stock_movements`.
- Don't use `localStorage` for anything that matters.
